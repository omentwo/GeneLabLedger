## 0. 总体结论

工程成熟度明显高于同类内部工具：Ruff、vue-tsc、133 个 pytest、287 个 Vitest、18 个 node:test 全部通过，事务边界、乐观并发、备份校验、Electron 沙箱这几块做得比多数桌面项目严谨。

## 2. 后端

### B1【高】自定义字段的类型校验整体失效

`backend/app/services/field_validation.py:19-45`

```python
if system_key in {"block_number", "experiment_number"}:
    return value, []
return value, []          # ← 自定义字段直接放行
```

v0.13.0（commit `bdc0bf1`）移除"可配置校验规则"时，把 `data_type` 的基础校验一起删了：

- `number` 列可以写入 `"abc"`；
- `date` 列可以写入 `"明天"`；
- `select` 列可以写入不在 `FieldOption` 里的值。

而同一个文件里的 `validate_default_value`（:48-72）**仍然**校验 number/date/select，于是*出现*自相矛盾的行为：字段默认值必须是合法数字，单元格却能写任意文本。

影响面比想象的大，因为所有写入路径都经过 `validate_field_value`：

| 路径             | 位置                                                      |
| -------------- | ------------------------------------------------------- |
| 单格编辑           | `LedgerView.vue:4487` → `/records/cell-batches/preview` |
| 粘贴 / 填充 / 查找替换 | `cell_batches.preview_cell_changes` :332                |
| 快速录入           | `QuickEntryView.vue:1143`                               |
| 新增记录校验         | `api/records.py:585 validate_new_record`                |

连带后果：`number_between` 筛选和数值排序走 `func.strict_number()`，非法文本返回 NULL，这些行会在筛选/排序里"静默消失"，用户很难理解为什么某行不见了。

同时有三处描述已经过期：

- `field_validation.py:23` 注释仍写 "Normalize and validate one core **or custom** ledger cell"；
- `docs/technical.md:100` 仍写"先预检查字段类型、选项"；
- `validate_field_value` 的 `FieldValueIssue.severity` 已经只可能产出 `error`，`suggestion` 分支成了死枚举。

**建议**：要么恢复 `data_type` 级校验（不含可配置规则，只做 number/date/select 三件事），要么明确把 `data_type` 降级为"输入控件提示"并同步改文档、去掉 `strict_number` 的隐含依赖。

### B2【中】单条 PATCH 没有并发保护

`backend/app/api/records.py:827 update_record`

没有 `begin_immediate_write`，没有 `updated_at` / 版本比对，纯 last-write-wins。对比之下：

- 单元格批量：`expected_value` 比对 + `BEGIN IMMEDIATE`（`records.py:688`、`cell_batches.py:334`）；
- 按日期重排：`expected_order_hash` + `BEGIN IMMEDIATE`。

主台账单格编辑走的是批量接口（安全），但 `updateSelectedStatus`（见 B3）走 PATCH，是当前唯一一条"双窗口同时操作会互相覆盖"的写入路径。

### B3【中】批量状态修改 = N 次 HTTP + N 次事务

`frontend/src/views/LedgerView.vue:6344 updateSelectedStatus`

```ts
const updated = await mapInChunks(targets, (record) => updateRecord(record.id, { status }));
```

`mapInChunks` 每批 25 个并发。选中 1000 条就是 1000 次 `PATCH`、1000 次 `commit`、1000 条审计记录、1000 次 `updated_at` 变更。

而 `cell-batches` 接口本来就支持核心字段（`_apply_core_value`，`cell_batches.py:385`），一次 preview + 一次 commit 即可原子完成，还能复用"锁定跳过"和"警告确认"。

`updateSelectedLock`（:6366）同样是 N 次请求，且后端没有批量锁定接口。

### B4【中】关键字搜索是全表扫描

`backend/app/services/records.py:75-109 record_search_filter`

```sql
pathology_number LIKE '%term%' OR block_number LIKE '%term%'
OR experiment_number LIKE '%term%'
OR EXISTS (SELECT 1 FROM record_values WHERE value_text LIKE '%term%')
```

- 前导通配符使任何 B-Tree 索引失效；
- `record_values` 连普通索引都没有；
- 台账搜索框 100ms 去抖，每次输入都触发一次 `records × record_values` 全扫。

数据量到 5 万条 × 15 列时，单次搜索要扫 75 万行。**建议**：建 SQLite FTS5 虚拟表（内置能力，无需额外依赖），把三个核心列 + 拼接后的自定义值写入索引；或至少给 `record_values.value_text` 建索引以覆盖前缀匹配场景。

### B5【中】缺少 `(project_id, experiment_date)` 索引

`backend/app/models.py:133-137` 有 status / position / pathology 三个复合索引，唯独没有日期。而"显示范围按月""Dashboard 按月统计""实验日期筛选"全部按 `experiment_date` 过滤。

### B6【中】Dashboard 全量加载后在 Python 里聚合

`backend/app/api/dashboard.py:40-48`

```python
rows = session.execute(select(project_id, status, experiment_date, report_generated)).all()
```

10 万条记录会把 10 万 × 4 列拉进内存，再用 `Counter` 累加。完全可以交给 SQLite：

```sql
SELECT project_id, status, strftime('%Y-%m', experiment_date) AS m, COUNT(*)
FROM project_records GROUP BY 1, 2, 3
```

面板每次打开都重算，是当前最容易被数据量拖慢的页面。

### B7【中】导出上限 200 万格 + 纯内存拼 XML + 数字全变文本

三件事叠加：

1. `schemas.py:988-992` 允许 2,000,000 个单元格；
2. `services/workbooks.py:73` 用字符串 `join` 拼出整张表的 XML，2M 格约 200MB+ 中间字符串，峰值内存可能过 GB，且完全跑在 FastAPI 的同步线程池里；
3. `workbooks.py:67` 所有单元格都写成 `inlineStr` + `numFmtId=49`（文本格式），前端 `utils/workbook.ts:34` 又把值统一 `String(value)`。

结果是导出的 Excel 里数字列全部是"文本"，带绿色三角，不能直接求和/排序。如果这是为了保住病理号的前导零，应该只对文本列用文本格式，对 `data_type === "number"` 的列写 `<v>` 数值单元格。

### B8【中】未启用 WAL，且没有 `busy_timeout`

`backend/app/database.py:95-106` 只设了 `PRAGMA foreign_keys=ON`，没有 `journal_mode=WAL`，也没有 `busy_timeout`。

后果：

- 回滚日志模式下，备份线程的 `source.backup()` 与业务写入争用同一把写锁；`database_backups.py:236` 用 `pages=256, sleep=0.05` 缓解，但大库仍可能让前端看到 `database is locked`；
- SQLAlchemy 引擎没有设置 `timeout`，默认 5 秒拿不到锁就直接 `SQLITE_BUSY`，而代码里没有对 `OperationalError` 的专门处理，会冒泡成 500；
- 主窗口 + 快速录入窗口同时保存时属于真实并发场景。

SQLite 官方文档：WAL 让读写互不阻塞、fsync 更少，代价是 `-wal`/`-shm` 附属文件和 checkpoint。本项目是单机单进程，条件完全满足。而且恢复流程已经处理了 `-wal`/`-shm`（`database_backups.py:616-620`），切换不会破坏备份/恢复。

## 5. 可以借鉴的业界做法

| 做法                                 | 出处                                                                                                                                                             | 与本项目的关系                                                                                                                                                             |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **WAL 模式**                         | [SQLite 官方 WAL 文档](https://www.sqlite.org/wal.html)：读写不互斥、顺序 I/O、fsync 更少；代价是 `-wal`/`-shm` 与 checkpoint，且要求同机                                                 | 单机单进程完全满足；恢复流程已处理附属文件                                                                                                                                               |
| **FTS5 全文索引**                      | SQLite 内置模块                                                                                                                                                    | 直接解决 B4 的 `%keyword%` 全表扫描                                                                                                                                          |
| **Keyset 分页**                      | 相比 `OFFSET` 分页，`WHERE (position, id) > (?, ?)` 在并发写入下不会跳行/重复                                                                                                   | `queryAllRecordBatches` 现在用 offset 循环，编辑期间刷新存在理论上的跳行                                                                                                                |
| **同步路由跑在线程池**                      | [FastAPI Best Practices](https://github.com/zhanymkanov/fastapi-best-practices/blob/master/README_ZH.md)：`def` 路由跑在 anyio 线程池（默认 40），`async def` 里做阻塞操作会卡死事件循环 | 项目把 Office COM 放进 `multiprocessing`（`office_printing.py:217`、`office_preview.py:364`）是正确做法，不要改成线程                                                                   |
| **localhost 服务加 per-launch token** | Electron 安全建议                                                                                                                                                  | `/api/desktop/shutdown` 已经用了 token（`system.py:79-96`），但业务接口只靠 CORS `allow_origins=["null"]`。`null` origin 沙箱 iframe 也能拿到，随机端口是目前唯一屏障。可以把这个 token 模式推广到全部 `/api` 请求头 |
| **Composable 拆分**                  | Vue 3 官方推荐用组合式函数组织复用逻辑                                                                                                                                         | `useLedgerHistory` 已是正面例子，可作模板                                                                                                                                      |

## 6. 建议的优先级

**先做（投入小、收益直接）**
